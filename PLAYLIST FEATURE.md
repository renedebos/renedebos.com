# Playlist Generator Feature Spec

## Goal

Let visitors build custom playlists from the Hannan archive, filtered by
artist, tags, venue, recording type, and length — then share via link.

## Phase 1: Metadata catalog

**Status (2026-07-07): DONE pending tag review.** Catalog generating at build
(`assets/tracks.json`); vocabulary approved in `TAGS.md`; draft tags applied
to all 293 tracks (Claude, song-level judgment + mechanical `rarity`/`guest`
passes) — Rene reviewing 27 flagged songs + mood spot-checks. Publish runbook
step 5 now includes tagging new shows at publish time.

Implementation differs from the original sketch — the site had grown a track
schema since this spec was written, so the catalog *derives* from
`data/recordings.json` instead of being hand-maintained:

- `assets/tracks.json` is generated by `scripts/build.py`
  (`build_track_catalog()`), same pattern as `assets/search-index.json`.
  One entry per curated track:
  - `id` — `{show-slug}-{tracknum:02d}`, e.g. `jerry-19-broadway-2001-01-08-01`
  - `title` — song title
  - `artist` — show artist id as used site-wide: `jerry` | `sean` | `mad` | `seanjerry`
  - `performer` — per-track guest override (usually `null`)
  - `songwriter` — who wrote it: `Jerry Hannan & Sean Hannan` for originals,
    the writer for covers, `Traditional` for trad, `null` if unknown
    (dedicated field since 2026-07-07; replaced the attribution tags)
  - `showDate` — ISO date, `null` for undated shows
  - `venue` — `venue_short`, e.g. `19 Broadway`, `Sweetwater`, `Cafe Java`
  - `sourceType` — `aud` | `sbd`
  - `tags` — from `recordings.json`; controlled vocabulary lives in `TAGS.md`
  - `durationSec` — integer, parsed from the track's existing `duration`
    (no ffprobe pass needed — durations were already in `recordings.json`)
  - `file` — R2 MP3 key (replaces the sketched `r2Path`; streaming goes
    through the Worker `{worker}/stream?file={key}`, not the r2.dev base)
  - `ver` — 12-char MD5 prefix from `data/processing/<slug>.json`, for
    cache-busting, same as song pages
  - `url` — deep link to the track on its show page
- Tags are edited on tracks in `data/recordings.json` (publish runbook
  step 5) and flow into the catalog at build time — so new shows are tagged
  at publish and no separate pipeline step exists to forget.
- Pre-existing attribution tags (`Bruce Springsteen`, `Irish`, …) stay; the
  controlled playlist vocabulary is a second dimension. See `TAGS.md`.

## Phase 2: Filter + player UI (static, client-side)

**Status (2026-07-07): DONE.** Live at **`/playlist/`** (directory URL to
match `/search/` etc., not the sketched `playlist.html`).

- Page generated by `build_playlist()` in `scripts/build.py`; logic in
  `scripts/playlist.js` → deployed to `assets/playlist.js`. Vanilla JS,
  reuses the site's chip/search-result styles and the `WORKER`/`formatTime`
  globals from `player.js`. "Playlist" added to the site nav (and thereby
  the sitemap).
- Facet filters: artist, venue, AUD/SBD (single-select chips) + tags
  (multi-select chips, AND semantics). Songwriter is in the catalog but has
  no facet — provenance tags cover it; /search/ handles by-writer lookup.
- Length modes: N songs / N minutes (greedy fill after shuffle) / endless
  shuffle (whole filtered pool, reshuffles and continues when it runs out).
- One shared `<audio>` queue: prev (restarts current track past 3 s) /
  play-pause / next, seekable progress bar, sticky now-playing card,
  clickable queue rows, Media Session metadata for lock screens.
- Streams via the Worker `/stream?file=&v=` (Range-verified) — the r2.dev
  public base named below no longer exists; the bucket is private.

## Phase 3: Stateless sharing

- “Share” button encodes the exact track ID list (base64) into the URL hash
  fragment, e.g. `/playlist.html#p=eyJ0cmFja3MiOls...`
- Loading a share URL hydrates the player with that exact list
- Optional: “recipe” links (filter criteria + shuffle seed) so a link can
  regenerate a reproducible — or intentionally fresh — playlist

## Phase 4: Short links (Cloudflare Worker + KV)

- New Worker `playlist-share`:
  - `POST /api/playlist` — store tracklist JSON in KV, return short slug
  - `GET /play/{slug}` — fetch list from KV, redirect/render player
- Short URLs like `renedebos.com/play/f8x2q`
- Follow existing patterns from the `wav-download` and `contact-form` Workers
- Consider KV TTL vs. permanent storage (recommend: no expiry; playlists are tiny)
