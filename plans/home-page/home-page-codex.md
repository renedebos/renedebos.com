## Repository Findings for the Icon

The visible mark is generated by `HOME_SHELL` in
`scripts/sitegen/pages.py`:

```html
<a class="mark" href="/" aria-label="The Hannan Tapes — home">♪</a>
```

Its circle, size, colors, hover state, and focus state are defined by `.mark`
in `scripts/home.css`. The built copies are `index.html` and
`assets/home.css`; they must be regenerated rather than edited directly.

Several other musical or circular symbols exist and should not be swept into
this first change:

- the home-page favicon is another musical note;
- show cards use a three-ring record/reel SVG in `scripts/home.js`;
- playlist rows and other generated pages also use musical-note icons; and
- non-home pages have their own generated shell and styling.

This is why the plan isolates the header mark and treats the favicon as a
separate yes/no decision.

## Recommended Working Rules

1. One project equals one branch plus one worktree folder.
2. One active editing session owns that worktree at a time.
3. Start every session by checking `pwd` and
   `git status --short --branch`.
4. Ask the session to read the root `CLAUDE.md` and the two files in
   `plans/home-page/` before making changes.
5. Keep `main` as the clean integration branch. Develop and commit on
   `home-page`.
6. Do not copy changed files manually between folders. Move work through
   commits, pushes, and pull requests.
7. If another project needs the same source lines, finish or coordinate one
   pull request before merging the other; Git will flag conflicts, but the
   planning files should warn about them early.

A useful opening prompt for a future session is:

```text
Work only in /home/renedebos/renedebos.com-home-page on the home-page branch.
Read CLAUDE.md, plans/home-page/home-page.md, and
plans/home-page/home-page-codex.md first. Confirm the branch and current Git
status before editing. Keep this task limited to the home-page header icon.
Do not commit, push, or merge until I ask.
```

## GitHub Flow for This Project

GitHub continues to contain one repository. Branches do not require separate
GitHub repositories or separate project folders on the website host.

When the local work is ready for review:

```bash
git status --short --branch
git diff
git add plans/home-page scripts/sitegen/pages.py scripts/home.css index.html assets/home.css
git commit -m "Replace home page header icon"
git push -u origin home-page
```

The exact `git add` list should match the actual reviewed diff; omit files
that did not change. After the push, open a pull request with:

```text
base:    main
compare: home-page
```

The pull request is the safety checkpoint: inspect the changed files, confirm
the build, and merge only when the result looks right. The live deployment
should continue to come from `main`, not directly from the feature branch.

## Adding a Future Parallel Project

Create a new branch and worktree from an up-to-date `main`, using a short,
descriptive project name. Conceptually:

```bash
git -C /home/renedebos/renedebos.com switch main
git -C /home/renedebos/renedebos.com pull --ff-only
git -C /home/renedebos/renedebos.com worktree add \
  -b <project-name> /home/renedebos/renedebos.com-<project-name> main
```

Then point the new Claude or Codex session at that new folder. A Git branch
can be checked out in only one worktree at a time, so every concurrent
project must use a different branch.

Before creating another worktree, check the existing map with:

```bash
git worktree list
```
